## Body

## What happens

`gen_list()`'s duplicate check is a linear scan over every line kept so far, so
`list -n 2000` is quadratic in the number of generated lines:

| command | median of 7 |
|---|---:|
| `psgen list` (181 lines) | 0.61 ms |
| `psgen list -n 500` | 2.68 ms |
| `psgen list -n 1000` | 7.43 ms |
| `psgen list -n 2000` | 21.46 ms |
| `psgen table -n 5000` (5× the rows, no dedup) | 46.25 ms |

Doubling the request from 1000 to 2000 lines multiplies the time by three, which
is the signature of the quadratic scan; for comparison the whole 5000-row table
costs 46 ms. Nothing here is fatal —
the cap is 2000 lines — but the cost is avoidable and the fix is four lines.

Cause: `src/gen.rs`, `gen_list()`:

```rust
let mut seen: Vec<Vec<u8>> = Vec::new();
let uniq = opts.uniq;
let push = |cmd: Vec<u8>, out: &mut Vec<Vec<u8>>, seen: &mut Vec<Vec<u8>>| {
    if !uniq || !seen.iter().any(|s| s == &cmd) {   // <- O(n) per line, O(n²) total
        seen.push(cmd.clone());
        out.push(cmd);
    }
};
```

The second pass rejects duplicates by retrying (`guard` up to `target * 40 + 1000`),
so the list is short but the scan is not.

## Patch (verified)

Keep `seen` sorted and binary-search it. A `HashSet<Vec<u8>>` is the other
option; a sorted `Vec` keeps the crate free of hashing and makes the failure
mode (a collision) impossible.

```diff
--- a/src/gen.rs
+++ b/src/gen.rs
@@ -324,12 +324,17 @@
 pub fn gen_list(rng: &mut Rng, opts: &Opts) -> Vec<Vec<u8>> {
     let mut out: Vec<Vec<u8>> = Vec::new();
+    // Kept sorted so the duplicate check is a binary search: a linear scan
+    // over every line already kept made `list -n 2000` quadratic.
     let mut seen: Vec<Vec<u8>> = Vec::new();
     let uniq = opts.uniq;
     let push = |cmd: Vec<u8>, out: &mut Vec<Vec<u8>>, seen: &mut Vec<Vec<u8>>| {
-        if !uniq || !seen.iter().any(|s| s == &cmd) {
-            seen.push(cmd.clone());
-            out.push(cmd);
+        if uniq {
+            match seen.binary_search(&cmd) {
+                Ok(_) => return,
+                Err(pos) => seen.insert(pos, cmd.clone()),
+            }
         }
+        out.push(cmd);
     };
```

Measured on the same host: `list -n 2000` 21.66 ms → 10.61 ms. The remaining
10 ms is generation plus `Vec::insert`'s memmove; if that ever matters, a
`HashSet` removes it, and the ordering of `out` is unaffected either way because
`seen` is only used for membership.

Verified: same line count and same distinct output at `-n 2000` (0 duplicates),
`--no-uniq` unaffected (2000 lines), and `tests/smoke.sh` passes. `list -n 0`
still prints the corpus in corpus order.

## Environment

psgen 0.0.1-beta.1 x86_64-unknown-linux-musl, 12-CPU Linux 7.2.11, medians of 7
runs of the release binary.

### Nemo-010 - 2026-11-09T03:40:37Z

Reproduced, and the numbers here are the same shape (this cage has 12 vCPU, so slightly faster):

| command | median of 7 |
|---|---:|
| `list` (181) | 1.22 ms |
| `list -n 500` | 2.57 ms |
| `list -n 1000` | 5.83 ms |
| `list -n 2000` | 14.29 ms |
| `table -n 5000` | 56.26 ms |

1000 → 2000 multiplies by 2.45, which is the quadratic scan. A sorted `Vec` + `binary_search` keeps the crate hash-free and makes the failure mode impossible; a `HashSet<Vec<u8>>` is the other option if the extra allocation is acceptable at 2000 entries.

One thing to check when you land it: `gen_list` also uses `seen` for the `--no-uniq` path, where `push` skips the check entirely. Keeping `seen` sorted only on the `uniq` branch is enough, but the insert has to stay O(log n) + memmove, which at 2000 entries is still ~2 ms of memmove worst case — the `HashSet` may actually win at the cap. Not addressed on `qa/verified-fixes` in `Nemo-010/psgen`.
