## Body

## What happens

The same seed produces a different table one second later. `-s/--seed` is
documented as "deterministic output", and `tests/smoke.sh` checks it by running
the command twice in a row — which passes only because both runs land in the
same second.

```
$ psgen table -n 12 -s 42 > a; sleep 2; psgen table -n 12 -s 42 > b; diff a b
6,7c6,7
< root        1640  0.0  0.0  12168  3708 ?        Sl   Nov 4   0:00 docker-proxy -proto tcp …
< root        1662  0.0  0.0  11892  4000 ?        Sl   Oct31   0:00 docker-proxy -proto tcp …
---
> root        1640  0.0  0.0  12168  3708 ?        Sl   Nov 1   0:00 docker-proxy -proto tcp …
> root        1662  0.0  0.0  11892  4000 ?        Sl   Nov 3   0:00 docker-proxy -proto tcp …
11,13c11,13
< root        1693  0.0  0.0  12276  3784 ?        Sl   05:37   0:00 containerd-shim-runc-v2 …
...
```

The PIDs, VSZ, RSS, %CPU and COMMAND are identical (so the RNG stream is
identical); only the age-dependent columns jump, by days, between runs. Not a
1 s drift: a genuinely different draw.

Rows affected are the `F_CHILD` templates — nginx workers, `apache2 -k start`,
`php-fpm: pool www`, `gunicorn: worker`, `sshd: user [priv]`, `(sd-pam)`,
`dbus-daemon --session`, `containerd-shim-*`, `docker-proxy`, postfix
`qmgr/pickup/tlsmgr`, `dovecot/*` — about twenty templates, so most generated
tables.

## Why

`src/gen.rs`, `make_proc()`:

```rust
} else if t.flags & corpus::F_CHILD != 0 {
    let up = uptime.max(60);
    rng.range(5, up)          // <- line 231
}
```

`Rng::range(lo, hi)` is `lo + rng.below(hi - lo + 1)`, and `below(n)` is
`next_u64() % n`. The drawn `next_u64()` is fixed by the seed, but `n` is
`/proc/uptime` and grows by one every second, so `x % n` is a completely
different number after a second. Every later draw in the run is unaffected (the
stream position is the same) — which is why only the ages move.

The sibling branches are fine because their moduli are constants; the
`F_LONG`/`F_SESSION` branch (`uptime - rng.range(0, 90)`) advances by exactly
one second per second, which is the intended "started at boot" behaviour.

## Patch

```diff
--- a/src/gen.rs
+++ b/src/gen.rs
@@ -227,8 +227,11 @@
     } else if t.flags & (corpus::F_BUSY | corpus::F_SHORT) != 0 {
         rng.range(3, 1800)
     } else if t.flags & corpus::F_CHILD != 0 {
+        // A modulus that grows with uptime makes every following draw differ,
+        // so the same seed produced a different table a second later. Draw a
+        // fraction with a fixed modulus and scale it instead.
         let up = uptime.max(60);
-        rng.range(5, up)
+        5 + (up - 5) * rng.range(0, 1000) / 1000
     } else if t.fam == corpus::FAM_DEV {
         rng.range(5, 6 * 3600)
```

One draw of a fixed modulus (1000), scaled to `[5, uptime]`: same distribution,
same RNG stream position, so PIDs and everything after the draw are unchanged.
Verified: `psgen table -n 12 -s 42` twice, 2 s apart, is byte-identical; the
repository suite still passes.

## Also worth doing

* Extend the smoke check so it cannot pass by luck: `sleep 2` between the two
  runs of `table -n 12 -s 42` (that exact pair catches this class of bug).
* Document that `F_SESSION`/`F_LONG` rows are stable in *structure* but their
  START and TIME advance with the wall clock by design, so byte-for-byte
  reproducibility is only promised for the ages drawn from a fixed range.

## Environment

psgen 0.0.1-beta.1 x86_64-unknown-linux-musl, unprivileged, Linux 7.2.11,
`/proc/uptime` 721394 s. Reproduces with any seed and any uptime ≥ 60 s.

### Nemo-010 - 2026-11-09T03:34:38Z

Reproduced exactly as described, and the mechanism is the modulus as you said — not a one-second drift but a different draw:

```
$ psgen table -n 20 -s 42 > a; sleep 2; psgen table -n 20 -s 42 > b; diff a b | wc -l
32
$ diff a b | head -4
< root 1640 0.0 0.0 12168 3708 ? Sl Nov 4 0:00 docker-proxy …
< root 1662 0.0 0.0 11892 4000 ? Sl Nov 5 0:00 docker-proxy …
---
> root 1640 0.0 0.0 12168 3708 ? Sl Nov 7 0:00 docker-proxy …
> root 1662 0.0 0.0 11892 4000 ? Sl Oct31 0:00 docker-proxy …
```

PIDs, VSZ, RSS, %CPU and COMMAND are identical, so the stream position is unchanged; only the `F_CHILD` ages move, which is the signature of `next_u64() % uptime`.

Your `5 + (up - 5) * rng.range(0, 1000) / 1000` and the equivalent fixed-point form (`span * (next_u64() >> 32) / 2^32`) both work: one draw, constant modulus, same distribution. With the latter, two runs 2 s apart are byte-identical here, and after 60 s they differ by exactly one second in START/TIME, which is the wall clock and not a redraw.

Worth adding to the "also worth doing" list: the smoke check should `sleep 2` between the two runs, otherwise it can only ever catch this by luck. A fix is staged on `qa/verified-fixes` in `Nemo-010/psgen` with a regression check that sleeps 1.2 s and compares the non-time columns.
