## Body

## What happens

`test/smoke.sh` → `tests/invariants.py` aborts on three host properties that are
normal in a container and none of them are psgen's fault. Each abort kills the
whole suite (`FAIL:` + `raise SystemExit(1)`), so on such a host CI reports the
test harness as broken rather than the code.

### 6a. A finite hard `RLIMIT_FSIZE` → `subprocess.SubprocessError` in `preexec_fn`

```
$ ulimit -Hf
976562                     # 953 MiB, common in containers
$ sh tests/smoke.sh
  File "/…/tests/invariants.py", line 970, in check_load
    p = limited(["load", "--disk-util", "2048"], 1024 ** 3)
  File "/…/tests/invariants.py", line 956, in limited
    return subprocess.run(…, preexec_fn=preexec)
subprocess.SubprocessError: Exception occurred in preexec_fn
```

`limited()` asks for a soft limit of 1 GiB while the inherited hard limit is
953 MiB, and `resource.setrlimit` refuses to raise a soft limit above the hard
one:

```python
def preexec():
    soft, hard = resource.getrlimit(resource.RLIMIT_FSIZE)
    lim = hard if fsize is None else fsize          # 1 GiB > hard → ValueError
    resource.setrlimit(resource.RLIMIT_FSIZE, (lim, hard))
```

Patch — clamp to the hard limit, which is all the assertion needs (2048 MiB
still exceeds any hard limit the test can install):

```diff
-            lim = hard if fsize is None else fsize
+            # a soft limit can never exceed the hard limit: clamping keeps the
+            # guard test runnable on a host whose hard RLIMIT_FSIZE is finite
+            lim = hard if fsize is None else (
+                fsize if hard == resource.RLIM_INFINITY else min(fsize, hard))
```

The neighbouring free-space guard already detects this case and prints
`free-space guard not reachable: RLIMIT_FSIZE is 953 MiB`; the RLIMIT guard has
no such fallback.

### 6b. No `/dev/ptmx` → the pty assertion fails

```
FAIL: no injected process acquired a pty
```

`psgen doctor` correctly reports `pty DENY /dev/ptmx open failed (errno 2)` and
`inject` reports `tty 0 real, 0 degraded`, i.e. the tool is honest about it; the
test asserts unconditionally:

```python
rows = ps_rows()
if not any(rows.get(p) and rows[p]["tty"].startswith("pts/") for p in pids):
    fail("no injected process acquired a pty")
```

Patch — skip when the tool itself says the capability is missing (note: the
predicate depends on issue 8's JSON shape; with the current shape it is
`'"pty":{"ok":true'`):

```python
def can_pty() -> bool:
    """True when this host lets a process acquire a pty (doctor says so)."""
    p = run(["doctor", "--json"])
    return '"name":"pty","ok":true' in p.stdout.replace(" ", "")
…
if can_pty() and not any(rows.get(p) and rows[p]["tty"].startswith("pts/") for p in pids):
    fail("no injected process acquired a pty")
```

### 6c. A PID 1 that does not reap → "survived --duration"

```
FAIL: pid 3453 survived --duration 1
```

The three `--duration`/`--busy --duration` checks use `os.kill(pid, 0)` as a
liveness test, which succeeds for a zombie. In a container whose PID 1 never
reaps, every stub that dies on its alarm stays visible in `/proc` for ever (this
cage reached 645 zombies), so the test can never pass — and the same confusion
is what makes `stop` miscount (see the stop issue).

Patch, one helper and three call sites:

```python
def alive(pid: int) -> bool:
    """False when the PID is gone, or when it is a zombie left by a parent
    that never reaped it: either way there is nothing left to signal."""
    try:
        stat = Path(f"/proc/{pid}/stat").read_text()
    except OSError:
        return False
    return stat[stat.rindex(")") + 2] != "Z"
…
-            try:
-                os.kill(pid, 0)
-                fail(f"pid {pid} survived --duration 1")
-            except ProcessLookupError:
-                pass
+            if alive(pid):
+                fail(f"pid {pid} survived --duration 1")
```

(the same for `survived --wait --duration 1` and `--busy --duration 2 pid … survived`.)

## Verified

All three patches are applied to a scratch copy; `sh tests/smoke.sh` on the same
cage then runs to completion:

```
== version
== help
== corpus denylist and expanded output
== corpus dump
== list
== deterministic seed
== invariants and injection
free-space guard not reachable: RLIMIT_FSIZE is 953 MiB
root checks skipped: no passwordless sudo
invariants: ok
smoke: ok
```

Before the patches the suite stopped at the first of the three, i.e. none of the
later checks (stop identities, `--verify` exactness, `--cpu`, `--mem-target`,
`--phys-cap`, pidfile preflight) ran at all on this host.

## Environment

psgen 0.0.1-beta.1, Python 3.14, Linux 7.2.11, hard `RLIMIT_FSIZE` 953 MiB, no
`/dev/ptmx`, non-reaping PID 1. Each patch is independent.

All three patches verified here, in the same order you hit them: the suite aborts at 6a, then at 6b, then at 6c, and with all three it runs to completion. That host is identical in the relevant ways to yours — hard `RLIMIT_FSIZE` 953 MiB, no `/dev/ptmx`, non-reaping PID 1.

Two notes on the patches:

- 6b's predicate has to follow #8. With the current single-key shape, the check is `"pty":{"ok":true` after stripping spaces, which is what I used; once #8 becomes `{"name":"pty","ok":…}` it has to be `"name":"pty","ok":true`. Worth accepting both shapes so the two issues do not have to land in order.
- 6c's `alive()` is also the right shape for the `stop` accounting in #4: a `Z` is gone for both purposes.

These three are the last commit of the branch `qa/verified-fixes` in `Nemo-010/psgen`, because without them the report's own patch still aborts the suite on this kind of host — so they are a prerequisite for any green CI run, not a nicety.
