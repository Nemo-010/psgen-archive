## Body

`psgen table` emits physically impossible rows on a host smaller than the largest corpus template: RSS above `MemTotal`, `%MEM` above 100, and synthetic PIDs above `pid_max`. The corpus carries absolute sizes and the generator never compares them to the host.

## What happens

The corpus has absolute VSZ/RSS values. The largest is qemu:

```rust
t!("qemu-system-x86_64 -enable-kvm -m 4096 …", "libvirt-qemu", FAM_CTR,
   4200000, 2080000, 12, 1, F_THREADS, 3),
```

4,200,000 KiB VSZ / 2,080,000 KiB RSS. `src/table.rs` then computes `%MEM` against the
host's `MemTotal` with no clamp:

```rust
let mem = if mem_total_kb == 0 { 0 } else { (rss * 1000 / mem_total_kb) as u32 };
```

On a host with 12 GiB that is 7.4%, which is fine. On a 512 MiB container the same
row is 172% of `MemTotal`, and on a 1 GiB container 86%:

```
$ psgen table -n 400 -s 3 | awk 'NR>1{print $6}' | sort -n | tail -1
900788                     # kB, 880 MiB
$ # as a fraction of MemTotal:
12 GiB host:   7.4%
1 GiB cgroup:  86%
512 MiB cgroup: 172%
```

A single process cannot have an RSS larger than physical memory, and `%MEM` above 100
is impossible for one process. The `%MEM` field is also only four characters wide
(`push_tenths_width(mem, 4)`), so `172.0` overflows it and shifts every column after
it — the same class of defect as issue #3 item 3d, from the other direction.

The same applies to the 32-bit targets: a qemu row with 4.2 GiB VSZ cannot exist in a
32-bit address space at all.

## Second, separate case: PIDs above `pid_max`

`src/gen.rs` starts at `rng.range(300, 2500)` and adds 1..24 per row, so
`table -n 5000` reaches about 122,500:

```
$ psgen table -n 5000 -s 1 | awk 'NR>1{print $2}' | sort -n | tail -1
64248                       # on this host, pid_max 4194304
```

On a kernel with the historical `pid_max` of 32768 (still the default on some
embedded and container-tuned systems), those PIDs cannot exist and the table contains
impossible values. `pid_max` is readable from `/proc/sys/kernel/pid_max`.

## Why it matters

The tool exists to produce a *plausible* process table. A monitor, a dashboard or a
`ps aux` diff that consumes the output will either reject the row or, worse, believe
it. `%MEM` above 100 is the kind of thing an alerting rule fires on.

## Options

1. **Clamp to the host.** `rss = min(rss, mem_total_kb * 95 / 100)` and
   `mem = min(mem, 999)`. Cheap, keeps the row count, changes the sizes (which is
   already a lie, just a smaller one).
2. **Scale the corpus to `MemTotal`.** Multiply every template's VSZ/RSS by
   `min(1, mem_total_kb / largest_rss_kb * 0.8)`. Keeps the *relative* sizes, which is
   what a realistic table needs, and never exceeds the host. This is the option I
   would pick: a 512 MiB container should show a qemu at ~400 MiB, not at 2 GiB.
3. **Document the assumption** ("the table assumes a host at least as large as the
   largest template") and leave it. Cheapest, and wrong for the containers this tool
   is most useful in.

For `pid_max`, read `/proc/sys/kernel/pid_max` once and wrap or stop the synthetic PID
sequence below it, with a warning when the requested count cannot fit.

```diff
--- a/src/gen.rs
+++ b/src/gen.rs
-    let mut pid = rng.range(300, 2500) as i32;
+    let pid_max = util::pid_max().unwrap_or(4_194_304);
+    let mut pid = rng.range(300, 2500).min(pid_max.saturating_sub(1)) as i32;
     ...
-            pid += rng.range(1, 24) as i32;
+            pid += rng.range(1, 24) as i32;
+            if pid as u64 >= pid_max { pid = 300; }   // wrap, or stop with a warning
```

## Test that would have caught it

```python
mem = mem_total()
pid_max = int(open("/proc/sys/kernel/pid_max").read())
out = run(["table", "-n", "5000", "-s", "1"]).stdout
for line in out.splitlines()[1:]:
    f = line.split()
    rss, mempct, pid = int(f[5]), float(f[3]), int(f[1])
    if rss > mem:
        fail(f"RSS {rss} kB exceeds MemTotal {mem} kB")
    if mempct > 100.0:
        fail(f"%MEM {mempct} is impossible for one process")
    if pid > pid_max:
        fail(f"PID {pid} exceeds pid_max {pid_max}")
```

Run it under a cgroup with a small `memory.max` to exercise the small-host case
cheaply; `util::cgroup_mem_limit_kb()` already exists, so the table can see the limit.

## Environment

`bf80156` built with `cargo 1.99.1`, x86-64, Linux 7.2.11, `MemTotal` 12,131,920 kB,
`pid_max` 4,194,304. The 512 MiB / 1 GiB figures are computed from the same rows
against a smaller `MemTotal`; the qemu template's absolute size is the constant in
`src/corpus.rs`.
