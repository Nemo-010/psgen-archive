## Body

Twelve small, independent defects and documentation mismatches found while
running every flag. None of them blocks a beta; together they are the difference
between "works" and "reads like it was tested". Each item is standalone — pick
them off in any order, or split into separate issues if that suits the tracker.

## 13.1 `unit` names a systemd target that does not exist

`src/unit.rs:46`:

```rust
out.push_str("After=local-fs.target proc-fs-nets.target\n");
```

systemd ships no `proc-fs-nets.target` — checked against `units/meson.build` on
`systemd` main: 47 `.target` units, no such name. Every boot of the printed unit
logs `Failed to add dependency on proc-fs-nets.target, ignoring` (harmless, but
it is the first line an operator sees).

```diff
-    out.push_str("After=local-fs.target proc-fs-nets.target\n");
+    out.push_str("After=local-fs.target sysinit.target\n");
```

(`/proc` is a kernel mount and is always there; `sysinit.target` is the one that
guarantees the rest of the early boot is done.) Adding
`systemd-analyze verify` to CI, as suggested in #11, would have caught this.

While in the unit: `ConditionPathExists=/proc/self/stat` is evaluated by the
manager, not by the service, so it is always true and says nothing about the
service's own procfs. `/proc/1/stat` or no condition at all would mean what it
looks like it means.

## 13.2 `unit` accepts generation flags and forwards none of them

```
$ psgen unit -p desktop -f desk --no-mem -d 300 -n 40 | grep ExecStart
ExecStart=/…/psgen inject --quiet --pidfile /run/psgen.pid -n 40 -s 7
```

Only `-n`, `-s`, `--pidfile` and `--create-users` reach the unit. `-p`, `-f`,
`--mem/--no-mem`, `-d`, `--no-root`, `--no-user`, `--no-tty`, `--no-threads`,
`--cpu`, `--mem-cap`, `--mem-target` are parsed and dropped, so a unit written
from a desktop-profile preview injects server rows at boot with no warning.
`unit::render()` just needs the flags it was given:

```rust
pub fn render(count: usize, seed: u64, pidfile: &[u8], args: &Args) -> Buf {
    …
    out.push_str(" -n ");
    out.push_u64(count as u64);
    out.push_str(" -s ");
    out.push_u64(seed);
    for a in args.forwarded() {          // ["-p", profile, "-f", family, "--no-mem", "-d", n, …]
        out.push(b' ');
        out.push_bytes(&arg(a));
    }
```

(If rejecting the flags instead is preferred, that is #9; either is fine, doing
neither is the only wrong answer.)

## 13.3 `--verify` says "requires --mem" but only warns

`--help`: `--verify  compare each stub's real VSZ/RSS with the planned value;
requires --mem`. `README.md`: "`--verify` … requires `--mem`". The code warns and
continues:

```
$ psgen inject -n 2 --verify --no-mem --dry-run
psgen: --verify has no effect with --no-mem
```

`--wait` with a zero duration, by contrast, exits 2. Pick one: exit 2 for
`--verify --no-mem` (consistent with `--wait`), or change both texts to "has no
effect with --no-mem". The warning already exists, so the change is one line in
`cli.rs::run`.

## 13.4 `check --binaries` exits 0 with 148 of 181 executables missing

```
$ psgen check --binaries
templates: 181
expanded:  181
…
binaries found: 32
binaries missing: 148
missing: systemd-journald  <- /usr/lib/systemd/systemd-journald
…
$ echo $?
0
```

For a CI step ("are the corpus's paths sane on the build host") that exit code is
useless. Suggest: exit 1 when `binaries missing > 0` under `--binaries`, or split
the flag (`--binaries` reports, `--require-binaries` fails). Also note `check`
prints `templates: 181` even when `-f web` narrowed the run to 17 expanded rows —
say `templates: 181 (17 in family web)`.

## 13.5 `log`'s module aliases are undocumented

`log -m list` prints the 14 canonical names; `module_known()` (in `activity.rs`)
also accepts `access`, `apache`, `nginx`, `web`, `flog`, `boot`, `dmesg`,
`rustc`, `gcc`, `make`, `wget`, `curl`, `docker`, `dockerbuild`, `docker_rm`,
`dockerrmi`, `tf`, `playbook`, `kernel`, `pip`, `php`. All work; none are in
`--help`, `README.md` or the `-m list` output. Either list them (`-m list` could
print `weblog (access, apache, nginx, web, flog)`), or drop them.

Related: `--flame` is an accepted option that only errors ("`--flame` is not
supported; use `psgen load --cpu-util`") and appears in no document. If it is a
compatibility shim for an older name, say so in the error; otherwise delete it.

## 13.6 `load` writes its summary to stderr

```
$ psgen load --cpu-util 25 -d 3
psgen: load cpu 25% for 3s        # on stderr
```

It is an informational line, not a diagnostic, and `psgen load … | tee` shows
nothing. `inject`'s summary goes to stdout; this one should too.

## 13.7 `--create-users` without root is silently a no-op

```
$ psgen inject -n 2 --create-users        # non-root
psgen: user switching needs root; running as user (use sudo, --elevate, or --no-root)
psgen: reduced capability: pty=no (run `psgen doctor` for the errno)
```

The first warning implies sudo would fix it, but `useradd` needs root too, and
nothing says `--create-users` was ignored. `prepare()` already has the
`switch_users && !root` branch; add the same warning for `args.create_users &&
!root`: "`--create-users` needs root; no accounts were created".

## 13.8 A uid with no passwd entry renders as `user` in the synthetic table

`users::current()` falls back to the literal name `user` when `getpwuid_r` finds
nothing, so on a host (or a container) without a passwd entry for the caller:

```
$ psgen table -n 2 -s 7
user        1719 91.8 …   gcc -c -O2 …
$ inject -n 2 --pidfile /tmp/p.pid; ps aux | grep gcc
966          1719  0.0 …    gcc -c -O2 …          # ps shows the numeric uid
```

`ps` prints the numeric uid when it cannot resolve one, and the *injected* stub
does exactly that (its uid stays 966), so `psgen table` disagrees with the `ps`
output the same rows produce. Fallback to the decimal uid in
`users::current()`/`resolve_user()` and both agree; the `@self` rows then render
as `966` here and as the real login name on a normal host.

## 13.9 `corpus`'s `@self` sentinel is undocumented

`psgen corpus` prints 56 rows whose user column is `@self` (`corpus.rs`,
`SELF_USER`). The format is documented nowhere; a consumer parsing the dump gets
a user name that cannot exist. One sentence in the README (or substituting the
invoking user's name in the dump, which `list`/`table` already do) fixes it.

## 13.10 README/`--help` nits worth correcting

* README: "`table` defaults to 30 rows" — with the `sys` family in scope the
  output is 30 rows *including* PID 1, i.e. `table -n 30` ⇒ 30 rows, and the
  default (`table` with no `-n`) is also 30. That is right, but the next sentence
  ("`inject` to 12") sits next to `table` at 5000, so spell out that the count
  includes the injected PID 1 row when `sys` is in scope.
* README: "The pidfile is trusted input … a forged pidfile can name a process the
  caller may signal" — good, but it does not say the pidfile is *not* unlinked by
  `stop`, which is why re-running `inject` against the same path needs the file to
  be reusable (issue #1) and why `psgen unit` restart fails.
* `--help` lists `-q, --quiet` under INJECT only; `stop` accepts it and ignores
  it, and `--elevate` is listed under INJECT but also applies to `stop`
  (`cli.rs` handles both) — one line each.
* `--shadow-dir`: "the copy goes in a per-run subdirectory; ignored with
  `--no-exe`" is true, but `--shadow-dir` also forces the shadow tier under
  `--no-root`, which is the opposite of "ignored" in spirit; worth one clause.
* `-n` is "rows or commands" — for `unit` it is the *injected* count and for
  `doctor`/`corpus`/`stop` it does nothing (#9).

## 13.11 Repo metadata

`gh repo view` — description empty, no topics, 0 stars, and no `SECURITY.md`
while the README's Limitations section discusses forging pidfiles and spoofing
`/proc`. A two-line description (`Generate realistic Linux process lists, or
inject them into the real process table (static musl, 0BSD)`), topics
(`linux`, `procfs`, `process-table`, `monitoring`, `testing`, `rust`, `musl`),
and a `SECURITY.md` that says "this tool deliberately spoofs process state; do
not run it where a pidfile you did not write can be handed to `stop`" would cost
five minutes and close the "is this dormant?" question.

## 13.12 `tests/smoke.sh`'s `--version` grep

`tests/vm.sh:65` does `grep -q 'psgen 0.0.1'`, which is the same hardcoding as
#7 and will fail on the next version bump in a way that looks like a VM problem.
Read the version from `Cargo.toml` (`sed -n 's/^version = "\(.*\)"/\1/p'`, as
`release.yml` already does) or grep `'^psgen 0\.'`.
