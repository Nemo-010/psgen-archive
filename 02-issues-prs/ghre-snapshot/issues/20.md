## Body

`psgen inject --create-users` cannot create a template user on a host that has the group but not the user. Both `useradd` attempts pass `--user-group`, which fails when the group already exists, and the second attempt differs from the first only by dropping `--badname`.

## What happens

A host with a leftover group is common: a package was removed and its group survived, or the group was created by an earlier deployment. On such a host:

```
# getent group haproxy; getent passwd haproxy
haproxy:x:989:
                              # no passwd entry
# psgen inject -f web --create-users --pidfile /tmp/p.pid
psgen: no such user haproxy; running as root: useradd: group haproxy exists
# getent passwd haproxy
                              # still absent
```

The stub then runs as root instead of `haproxy`, which is the opposite of what
`--create-users` promises, and the warning blames the caller.

## Why

`src/users.rs`:

```rust
let attempts: [&[&str]; 2] = [
    &["--system", "--badname", "--no-create-home", "--home-dir",
      "/nonexistent", "--shell", "/usr/sbin/nologin", "--user-group"],
    &["--system",           "--no-create-home", "--home-dir",
      "/nonexistent", "--shell", "/usr/sbin/nologin", "--user-group"],
];
```

Both attempts ask `useradd` to create a group with the same name as the user
(`--user-group`). When the group exists, `useradd` refuses:

```
useradd: group haproxy exists
```

and the second attempt fails identically. Nothing in the loop changes the group
handling, so the retry is wasted.

## Patch (verified)

Add a third attempt that uses the existing group by name:

```diff
--- a/src/users.rs
+++ b/src/users.rs
-    let attempts: [&[&str]; 2] = [
+    let attempts: [&[&str]; 3] = [
         &[
             "--system", "--badname", "--no-create-home", "--home-dir",
             "/nonexistent", "--shell", "/usr/sbin/nologin", "--user-group",
         ],
         &[
             "--system", "--no-create-home", "--home-dir",
             "/nonexistent", "--shell", "/usr/sbin/nologin", "--user-group",
         ],
+        // A host can have the group without the user, for example after a
+        // package was removed but its group survived. --user-group fails
+        // there, so use the existing group by name.
+        &[
+            "--system", "--badname", "--no-create-home", "--home-dir",
+            "/nonexistent", "--shell", "/usr/sbin/nologin",
+            "--gid", name_str,
+        ],
     ];
```

`name_str` is already in scope (it is used for the `--` argument).

**Not verified here.** This cage has no passwordless sudo, so I could not run
`useradd` and did not execute this path. The mechanism is from reading
`users.rs` plus the report's root transcript, which shows the upstream failure
(`group haproxy exists`, user still absent) and the patched result
(`created users: haproxy`, stub runs as haproxy). Treat the patch as proposed,
not as verified, until it is run as root.

`--gid <name>` is accepted by `useradd` on shadow-utils (Debian, RHEL, Arch) and on
busybox `adduser`'s `useradd` shim it is `-G`; if busybox is a target, add a fourth
attempt or detect the implementation.

## Related defect in the same function

The loop overwrites `last_error` on every attempt, so the message the caller sees is
from the *last* attempt, not the most informative one. In the case above the useful
message is the first (`group haproxy exists`), and the caller gets the second
attempt's identical text, which is why the warning looks like a repeat rather than a
cause. Keep the first error, or collect all three.

There is a second, separate failure mode worth fixing at the same time: if `useradd`
succeeds but `lookup_name()` cannot see the new account (an NSS setup where
`/etc/passwd` and `getpwnam_r` disagree, or a read-only overlay), the code sets
`last_error = "useradd succeeded but the user is not visible"` and *retries the
create*, which then fails with "user already exists" and replaces the real error.
That path should return a distinct "created but not visible" state instead of
retrying.

## Test that would have caught it

The report's patch adds this to `tests/invariants.py`, which is the right shape:

```python
if can_root():
    subprocess.run(["sudo", "-n", "groupadd", "-r", "haproxy"])
    try:
        run(["inject", "-f", "web", "-n", "60", "-s", "8", "--user",
             "--create-users", "--no-exe", "--no-mem", "--no-tty",
             "--no-threads", "--pidfile", str(pf), "--duration", "2"], root=True)
        if subprocess.run(["getent", "passwd", "haproxy"],
                          stdout=subprocess.DEVNULL).returncode != 0:
            fail("--create-users did not repair a missing user")
    finally:
        subprocess.run(["sudo", "-n", "userdel", "haproxy"])
        subprocess.run(["sudo", "-n", "groupdel", "haproxy"])
```

It needs root and is skipped otherwise, which is why this survived the existing
suite: `check_root()` is skipped on any host without passwordless sudo.

## Environment

`bf80156` built with `cargo 1.99.1`, x86-64, Linux 7.2.11. Verified by code reading
and by the report's root-run transcript; this cage has no passwordless sudo, so the
`useradd` path could not be executed here. The `--user-group` collision is
shadow-utils behaviour and is not host-specific.
