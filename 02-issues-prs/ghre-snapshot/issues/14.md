## Body

`inject --pidfile` aborts with a panic *after* every stub has been spawned, so the run cannot be stopped and the staging directories are never cleaned up.

## What happens

`random_hex16()` is only called from `write_pidfile()`, and `write_pidfile()` runs after `spawn()` has forked the stubs and after the status records have been read. With `panic = "abort"` in both Cargo profiles, a failure there kills the process with no summary, no pidfile and no cleanup.

Trigger: any environment where `getrandom(2)` does not return the full 8 bytes. A seccomp policy that denies it, an interrupted call, or a kernel without the syscall all reach it.

```
$ # a 2-syscall seccomp launcher: SCMP_ACT_ERRNO(EPERM) for getrandom, then exec
$ ./sg ./psgen inject -n 2 --pidfile /tmp/e4.pid

psgen: reduced capability: pty=no (run `psgen doctor` for the errno)

thread 'main' (6734) panicked at src/inject.rs:555:18:
copy_from_slice: source slice length (8) does not match destination slice length (4)
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
Aborted (core dumped)

$ echo $?
134
$ ls /tmp/e4.pid
ls: cannot access '/tmp/e4.pid': No such file or directory
$ ps -eo pid,ppid,args --no-headers | awk '$2==1' | grep -E 'flanneld|cron -f|nginx: master'
    905       1 S    tail -f /var/log/nginx/access.log
   1608       1 Ss   /usr/bin/vim /etc/nginx/nginx.conf
   3573       1 S    nginx: master process /usr/sbin/nginx -g daemon on; master_process on;
$ ls -d .psgen-stubs/*
.psgen-stubs/.psgen-7593-9000-0
$ find .psgen-stubs -type f

```

The stubs are visible under their *template* argv, not under `psgen-stub`, so they look
like ordinary daemons in `ps` — which is the feature, and here is exactly why it is
dangerous: nothing about the row says it belongs to the aborted run.

The launcher, for reference (`libseccomp`; the report used `strace -e inject=getrandom:error=EPERM`):

```c
scmp_filter_ctx ctx = seccomp_init(SCMP_ACT_ALLOW);
seccomp_rule_add(ctx, SCMP_ACT_ERRNO(EPERM), SCMP_SYS(getrandom), 0);
seccomp_load(ctx);
execv(argv[1], &argv[1]);
```

## Why

`src/inject.rs`:

```rust
fn random_hex16() -> [u8; 16] {
    let mut raw = [0u8; 8];
    if !sys::getrandom(&mut raw) {
        raw[..4].copy_from_slice(&sys::getpid().to_le_bytes());
        raw[4..].copy_from_slice(&sys::monotonic_ns().to_le_bytes());  // <- line 555
    }
```

`raw[4..]` is four bytes; `u64::to_le_bytes()` is eight. `copy_from_slice` asserts equal lengths.

`write_pidfile()` is called from `run()` after `spawn()` returns, so the abort is strictly after the point of no return. `panic = "abort"` is set in `[profile.release]`, so there is not even an unwind-and-report path.

## Patch

```diff
--- a/src/inject.rs
+++ b/src/inject.rs
@@ -563,7 +563,9 @@ fn random_hex16() -> [u8; 16] {
     let mut raw = [0u8; 8];
     if !sys::getrandom(&mut raw) {
         raw[..4].copy_from_slice(&sys::getpid().to_le_bytes());
-        raw[4..].copy_from_slice(&sys::monotonic_ns().to_le_bytes());
+        // The buffer is 8 bytes and the tail is 4, so copy four bytes of
+        // the clock rather than the whole u64.
+        raw[4..].copy_from_slice(&sys::monotonic_ns().to_le_bytes()[..4]);
     }
```

Built and verified here: with the patch, the same launcher gives

```
$ ./sg ./psgen inject -n 2 --pidfile /tmp/x5.pid -q
psgen: user switching needs root; running as user ...
psgen: reduced capability: pty=no ...
$ echo $?; ls -l /tmp/x5.pid
0
-rw------- 1 966 965 154 Nov  9 02:18 /tmp/x5.pid
$ psgen stop --pidfile /tmp/x5.pid
stopped 2 processes
```

(The first line of the panic is dropped by the launcher's `exec`, which is why the `psgen:` warnings appear but the panic banner starts with a blank line.)

## Also worth doing (not part of the patch above)

Two independent hardening changes would make this class unreachable:

1. **Write the pidfile before spawning.** The PIDs are unknown then, but the boot id, the `# temp` lines and a placeholder are all known. Rewriting the file after the spawn is then an overwrite of a file the caller already has, and a failure there is recoverable.
2. **Turn `random_hex16` into a total function.** `getrandom` already has a fallback; the fallback should not be able to panic. A `uid`/`pid`/`monotonic_ns` mix into all 8 bytes is enough under 8 hex chars of context, and the collision domain here is a single directory.

## Test that would have caught it

Add to `tests/invariants.py`, next to the other pidfile cases:

```python
# a getrandom denial must not abort after the stubs are spawned
p = subprocess.run(["seccomp-launcher", "--deny", "getrandom", str(BIN),
                    "inject", "-n", "2", "--pidfile", str(pf), "--no-user",
                    "--no-mem", "--no-tty", "--no-threads"],
                   stdout=subprocess.PIPE, stderr=subprocess.PIPE, text=True)
if p.returncode != 0 or not pf.exists():
    fail(f"a denied getrandom aborted the run: rc={p.returncode}")
```

The launcher is 15 lines with `libseccomp`; a `strace -f -e inject=getrandom:error=EPERM`
wrapper works too, but needs `CAP_SYS_PTRACE`, which many CI containers do not have
(it is unavailable in the cage this was verified in, hence the launcher).

## Environment

`bf80156` built with `cargo 1.99.1` (release, `libc` only), x86-64, Linux 7.2.11,
unprivileged uid 966. Not root-specific and not arch-specific: `random_hex16` is the
same code everywhere.
