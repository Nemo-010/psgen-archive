# Azathothas/psgen#26: A pidfile basename near NAME_MAX passes the preflight and fails after the stubs are spawned

## Body

A pidfile path whose basename is close to `NAME_MAX` passes the preflight and then fails *after* the stubs have been spawned, because the preflight tests a short name and the writer appends a long suffix to the real one. The stubs are left running with no pidfile.

## What happens

The preflight is supposed to guarantee that the pidfile can be written before anything is spawned. It creates a short probe file in the *parent directory*:

`src/probe.rs`, `pidfile_creatable()`:

```rust
let parent = pidfile_parent(path);
let mut name = parent.to_vec();
if !name.ends_with(b"/") { name.push(b'/'); }
let mut b = Buf::new();
b.push_str(".psgen-probe-");
b.push_u64(sys::getpid() as u64);
b.push(b'-');
b.push_u64(sys::monotonic_ns());
name.extend_from_slice(b.as_bytes());
let fd = sys::open(&name, flags, 0o600);
```

and the real writer appends `.tmp.<pid>.<16 hex>` (about 25 bytes) to the **target
basename**:

`src/inject.rs`, `write_pidfile()`:

```rust
b.push_str(".tmp.");
b.push_u64(sys::getpid() as u64);
b.push(b'.');
b.push_bytes(&suffix);            // 16 hex chars
cand.extend_from_slice(b.as_bytes());
let f = sys::open(&cand, flags, 0o600);
```

So a basename that fits in `NAME_MAX` (255) can pass the preflight, and then the
`.tmp.…` name overflows it. Measured boundary on this host (`NAME_MAX` 255):

```
len=200  rc=0 written=yes
len=220  rc=0 written=yes
len=225  rc=0 written=yes
len=230  rc=1 written=no        <- from here up
len=235  rc=1 written=no
len=240  rc=1 written=no
```

The 230-byte case is the bad one:

```
$ psgen inject -n 2 --pidfile /tmp/nm3/ddd….dd
psgen: user switching needs root; running as user ...
psgen: reduced capability: pty=no ...
psgen: cannot write pidfile
spawned 2 processes; the pidfile was not written
exe tier shadow
reported RSS is shared; estimated physical cost 15 MiB
psgen: the pidfile was not written; spawned PIDs: 7350 7349
psgen: temp dir /workspace/qa/.psgen-stubs/.psgen-7344-9000-0
rc=1
```

Two stubs are running. The PIDs are dumped to stderr, which is better than nothing,
but a caller that treats a nonzero exit as "nothing was started" now has two
processes and a staging directory to clean up by hand. And the error message is
misleading: it says the parent is not writable, which is false.

## Why

Two independent problems:

1. **The preflight and the writer build different names.** One tests a ~30-byte
   name in the parent; the other writes a name derived from the target. They can
   never agree about a long target.
2. **`pidfile_error()` blames the wrong thing.** It checks `sys::is_dir(parent)` and
   `sys::access(parent, W_OK)` and concludes "the parent is not writable" for any
   failure past those. `ENAMETOOLONG` is not a permission problem.

## Patch (verified)

Make the preflight build exactly the name the writer will use, and report the
`NAME_MAX` case as what it is:

```diff
--- a/src/probe.rs
+++ b/src/probe.rs
-    let parent = pidfile_parent(path);
-    let mut name = parent.to_vec();
-    if !name.ends_with(b"/") { name.push(b'/'); }
-    let mut b = Buf::new();
-    b.push_str(".psgen-probe-");
-    b.push_u64(sys::getpid() as u64);
-    b.push(b'-');
-    b.push_u64(sys::monotonic_ns());
-    name.extend_from_slice(b.as_bytes());
     let flags = sys::O_WRONLY | sys::O_CREAT | sys::O_EXCL | sys::O_NOFOLLOW;
-    let fd = sys::open(&name, flags, 0o600);
-    if fd < 0 { return false; }
-    sys::close(fd);
-    let _ = std::fs::remove_file(...);
-    true
+    // Test the name `write_pidfile` will actually create, not a short probe
+    // name in the parent. A basename close to NAME_MAX passes a short probe
+    // and then fails after the stubs are spawned.
+    for _ in 0..8u64 {
+        let mut cand = path.to_vec();
+        let mut b = Buf::new();
+        b.push_str(".tmp.");
+        b.push_u64(sys::getpid() as u64);
+        b.push(b'.');
+        b.push_str(&format!("{:016x}", sys::monotonic_ns()));
+        cand.extend_from_slice(b.as_bytes());
+        let fd = sys::open(&cand, flags, 0o600);
+        if fd >= 0 {
+            sys::close(fd);
+            let _ = std::fs::remove_file(Path::new(OsStr::from_bytes(&cand)));
+            return true;
+        }
+        if sys::last_error().raw_os_error() != Some(libc::EEXIST) { return false; }
+    }
+    false
```

and distinguish "parent not writable" from "the name is too long":

```diff
--- a/src/cli.rs
+++ b/src/cli.rs
     } else if !sys::is_dir(parent) {
         out.push_str(" is not a directory");
-    } else {
+    } else if !sys::access(parent, sys::W_OK) {
         out.push_str(" is not writable");
+    } else {
+        out.push_str(" is writable but the file name cannot be created");
+        out.push_str(" (the name may exceed NAME_MAX once the temporary");
+        out.push_str(" suffix is added)");
     }
```

Verified:

```
$ psgen inject -n 1 --pidfile /tmp/namemax/ddd….dd      # 240 bytes
psgen: cannot write the pidfile /tmp/namemax/ddd….dd: the parent
/tmp/namemax is writable but the file name cannot be created (the name may
exceed NAME_MAX once the temporary suffix is added); use /tmp/psgen-pids.txt
$ echo $?
2                       # and nothing was spawned
```

220-byte basenames still work (`rc=0`, pidfile written), so the check is not simply
stricter than before.

## Test that would have caught it

```python
for length in (200, 220, 225, 230, 240, 250):
    name = "d" * length
    p = run(["inject", "-n", "1", "--no-user", "--no-mem", "--no-tty",
             "--pidfile", str(Path(tmp) / name)], check=False)
    if p.returncode != 0 and "spawned" in p.stdout:
        fail(f"basename {length} failed after spawning")
    if p.returncode == 0 and not (Path(tmp) / name).exists():
        fail(f"basename {length} reported success without a pidfile")
```

## Environment

`bf80156` built with `cargo 1.99.1`, x86-64, Linux 7.2.11, unprivileged uid 966,
`NAME_MAX` 255 on `/tmp` (tmpfs). The boundary (about `NAME_MAX - 25`) depends on the
length of the `.tmp.<pid>.<hex>` suffix, which is the point.
