## What happens

Two related things about the option surface.

### 9a. `-p/--profile` is listed under `COMMON` but only `table` and `inject` use it

`--help` puts `-p, --profile NAME  server (default), dev, desktop` in the COMMON
block, and `README.md` says "Common options are `-n/--count`, `-s/--seed`,
`-p/--profile` …". For `list` it does nothing at any realistic count:

```
$ psgen list -n 50  -s 1 -p server > a; psgen list -n 50  -s 1 -p desktop > b; diff a b | wc -l
0
$ psgen list -n 181 -s 1 -p server > a; psgen list -n 181 -s 1 -p desktop > b; diff a b | wc -l
0
$ psgen list -n 200 -s 1 -p server > a; psgen list -n 200 -s 1 -p desktop > b; diff a b | wc -l
48                                   # only the rows beyond the 181 templates
```

Cause: `src/gen.rs`, `gen_list()`. Rows up to the corpus size come from a first
pass in corpus order ("the first `target` templates"), and only the second pass
(the variants beyond 181) draws with `weighted_index(…, profile_weights(profile))`.
For `count == 0` the profile is not consulted at all.

The corpus-order first pass is not an accident: `tests/invariants.py` asserts it
(`list -n 5 --no-sort` must start with `/sbin/init`), and `list` with no `-n`
must print one line per template (181). So a fix has to either

* **document it** — say that `-p` weights only the rows beyond the corpus, and
  that `table`/`inject` are the profile-aware commands; or
* **reject it** — `-p` on `list`, `check`, `unit` exits 2 like `--force` on a
  non-stop command ("--force only applies to stop"); or
* **make it real** and relax the invariant — I tried that (weighted first pass,
  `pick_index`-style de-duplication) and it changes the tested contract, so it is
  a design decision rather than a bug fix: every short list re-orders, and
  `list -n 10 -p server` starts with whatever the weights pick, not `/sbin/init`.

`check` is in the same position: `check -p desktop` and `check -p server` produce
identical output because `gen::all_commands()` never looks at the profile.

### 9b. Every other option is accepted and silently dropped

`parse()` builds one global `Args` and `run()` picks what it needs, so a flag
that belongs to another subcommand is a no-op instead of an error:

```
$ psgen stop -n 40 --pidfile /tmp/x.pid         # -n ignored
stopped 0 processes, skipped 1
$ psgen corpus -n 5 | wc -l                     # -n ignored
181
$ psgen list -d 5 -n 1 >/dev/null               # -d ignored
$ psgen list --json -n 1                        # --json ignored, prints a command line
/sbin/init
$ psgen table --live -f web | wc -l             # -f ignored for --live
680
$ psgen doctor --json --lines 5 >/dev/null      # --lines ignored
$ psgen check --utc-offset 300 | head -1        # --utc-offset ignored
templates: 181
$ psgen unit -p desktop -f dev --no-mem -d 60 | grep ExecStart
ExecStart=/workspace/qa/bin/psgen inject --quiet --pidfile /run/psgen.pid -n 24 -s 7
```

The last one is the one that bites: `unit` accepts `-p`, `-f`, `--mem/--no-mem`,
`-d`, `--no-root`, `--threads`, `--tty`, `--cpu`, `--table`, `--verify`, and the
generated unit contains none of them — it always runs `inject --quiet --pidfile
… -n <count> -s <seed>` (only `-n`, `-s`, `--pidfile` and `--create-users` are forwarded; the
"make `unit` forward them" half of the fix is written up in #13, item 2). Someone who
writes `psgen unit -p desktop -n 40` gets a unit that injects 40 *server* rows
and no warning.

`--force` already shows the shape of the fix (`cli.rs`):

```rust
if a.force && a.sub != Sub::Stop && a.sub != Sub::Help && a.sub != Sub::Version
    && !a.want_help && !a.want_version
{
    return Err("--force only applies to stop");
}
```

## Step (not applied here)

Give each flag the set of subcommands that consume it and reject the rest in
`parse()`, after the argv walk, where `a.sub` is known:

```rust
fn allowed(sub: Sub) -> &'static [&'static [u8]] {
    match sub {
        Sub::Stop => &[b"--force", b"--pidfile", b"--elevate", b"-q", b"--quiet"],
        Sub::Check => &[b"-s", b"--seed", b"-f", b"--family", b"--binaries", b"-p", b"--profile"],
        Sub::Corpus => &[],
        Sub::Unit => &[b"-n", b"--count", b"-s", b"--seed", b"--pidfile",
                       b"--create-users", b"-p", b"--profile", b"-f", b"--family",
                       b"--no-mem", b"-d", b"--duration", b"--no-root", b"--no-user",
                       b"--no-tty", b"--no-threads", b"--cpu", b"--mem-cap", b"--mem-target"],
        …
    }
}
```

Two paths, pick one:

* **reject**: record every option name seen during the walk and, in one pass at
  the end, error with `"<option> does not apply to <sub>"` (exit 2, like
  `--force`). No behaviour change for correct usage, and it catches typos such as
  `psgen inject --famly dev`.
* **forward**: at minimum make `unit` pass through what it accepts. `unit` is the
  natural home for a full round trip — `psgen unit -p desktop -f desk --no-mem
  -d 300` should print a unit whose `ExecStart` contains exactly those flags, so
  that `systemctl start` reproduces the table you were looking at.

Either way, the COMMON section of `--help` and the README should say which
commands honour `-p` today, so nobody else spends an afternoon diffing two
identical lists.
