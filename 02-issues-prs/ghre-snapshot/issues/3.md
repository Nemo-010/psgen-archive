## Body

Four deviations between `psgen table --live` (and `inject --table`) and
`ps aux` (procps-ng 4.0.7). The header is byte-identical and normal rows match,
so these are the cases a monitor or a diff would actually hit. Each has a
one-place fix; 3a, 3b and 3d are verified against this tree.

## 3a. A newline in `/proc/PID/cmdline` splits the row (worst of the four)

Any process whose argv contains a `\n` — a `bash -c` with a multi-line script,
`vim`, `sed -e`, a python `-c`, anything generated by a wrapper — makes
`table --live` emit a broken row followed by plain text:

```
$ python3 -c 'import subprocess,time,sys
p=subprocess.Popen([sys.executable,"-c","import time;time.sleep(20)","line1\nline2","tab\there","\x01ctl"])
time.sleep(0.4)'
$ psgen table --live | grep -A2 'line1'
966         4960  0.0  0.0  20488  9108 ?        S    13:04   0:00 /usr/bin/python3 -c import time;time.sleep(30) line1
line2
tab	here
ctl
```

Everything after the first `\n` is lost as columns; in one capture 23 of the
lines were junk, and any consumer parsing columns (the repo's own
`bench/measure.py`, `tests/invariants.py`, `awk`-by-field) silently drops the
row. `ps` never does this:

```
$ ps -o pid,args -p <pid>
4960 /usr/bin/python3 -c import time;time.sleep(20) line1 line2 tab?here ?ctl
```

i.e. `\n` and `\r` become a space, every other C0 byte and DEL become `?`.

Cause: `src/live.rs`, `read_cmdline()` copies argv bytes verbatim after turning
NUL into a space.

```diff
--- a/src/live.rs
+++ b/src/live.rs
@@ -158,10 +158,18 @@
     let mut out = Vec::with_capacity(n);
     for b in &buf[..n] {
         if *b == 0 {
             if out.last() != Some(&b' ') {
                 out.push(b' ');
             }
+        } else if *b == b'\n' || *b == b'\r' {
+            // ps never writes a raw line break into COMMAND: it would split
+            // the row and lose every column after it.
+            out.push(b' ');
+        } else if *b < 0x20 || *b == 0x7f {
+            out.push(b'?');
         } else {
             out.push(*b);
         }
     }
     str::trim(&out).to_vec()
```

Verified: the same process now renders `… line1 line2 tab?here ?ctl`, identical
to `ps`, on one line.

## 3b. Zombies lose `<defunct>`

```
$ ps -o pid,stat,args -p 407
    407 Z    [sleep] <defunct>
$ psgen table --live | awk '$2==407'
966          407  0.0  0.0      0     0 ?        Z    12:19   0:00 [sleep]
```

`ps` appends ` <defunct>` to COMMAND for a zombie. In a container whose PID 1
does not reap, this is the *normal* state of every process that ever exited, so
the live table is full of rows that `ps` shows differently.

```diff
--- a/src/live.rs
+++ b/src/live.rs
@@ -188,13 +188,16 @@
-    let cmd = if cmd.is_empty() {
+    let mut cmd = if cmd.is_empty() {
         let mut b = Buf::new();
         b.push(b'[');
         b.push_bytes(&stat.comm);
         b.push(b']');
         b.v
     } else {
         cmd
     };
+    if stat.state == b'Z' {
+        cmd.extend_from_slice(b" <defunct>");
+    }
```

Verified: `[sleep] <defunct>`, `[flanneld] <defunct>` as `ps` prints them.

## 3c. `inject --table` is not PID-sorted

`ps aux` is PID-ordered and `table --live` is (it sorts `/proc` entries), but
`--table` renders in pidfile order, so a just-injected table looks shuffled:

```
USER         PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
966         2764  0.0  0.0  15444  4824 ?        S    12:50   0:00 nginx: cache manager process
966         2763  0.0  0.0  13160  8156 ?        S    12:50   0:00 nginx: master process …
```

One line in `src/live.rs`, `read_pids()`:

```rust
pub fn read_pids(pids: &[i32]) -> Vec<Proc> {
    …
+   rows.sort_unstable_by_key(|p| p.pid);
    rows
}
```

## 3d. A wide numeric field shifts every column after it

With a process whose VSZ is 8 digits (Chrome, java, kubelet, anything with a
big heap — the reference process on this host is 74195184 kB), `ps` keeps STAT,
START, TIME and COMMAND at the header offsets by letting the overflow eat the
TTY padding; psgen keeps an eight-wide TTY field and pushes the rest right:

```
ps   : 966            1  8.4  1.1 74195184 141108 ?     Sl   12:00   8:13 /usr/local/bin/…
psgen: 966            1  8.4  1.1 74195184 140608 ?        Sl   12:00   8:08 /usr/local/bin/…
                                                      ^ stat at 52, START at 57, COMMAND at 70 (ps: 49/54/67)
```

Cause: `src/table.rs`, `render()` pads TTY to a fixed width of 8 and then adds a
space, so the row length decides where STAT lands. Pad to the absolute column
instead:

```diff
--- a/src/table.rs
+++ b/src/table.rs
@@ -141,6 +141,7 @@
     for p in rows {
+        let row_start = out.v.len();
         let vsz = round_up(p.vsz as u64, page_kb);
@@ -158,15 +159,19 @@
-        let tty_start = out.v.len();
         tty_field(&mut out, p);
-        let tty_len = out.v.len() - tty_start;
-        let mut pad = 8usize.saturating_sub(tty_len);
-        while pad > 0 {
+        // Pad to the absolute STAT column. ps keeps STAT/START/TIME at the
+        // header offsets when a numeric field is wider than its slot, so the
+        // overflow eats the TTY padding instead of shifting the line; a fixed
+        // eight-wide TTY field pushed every column after it to the right.
+        const STAT_COL: usize = 49;
+        if out.v.len() - row_start < STAT_COL {
+            while out.v.len() - row_start < STAT_COL {
+                out.push(b' ');
+            }
+        } else {
             out.push(b' ');
-            pad -= 1;
         }
-        out.push(b' ');
         stat_field(&mut out, p);
```

Verified: 1908 live rows compared with `ps aux` on this host, comparing the
offsets of the STAT, START and TIME tokens per row (what a fixed-column consumer
sees). Before the patch: 1 mismatch — pid 1, the only process here with a 7+
digit VSZ. After: 0, with pid 1 rendering `?     Sl   12:00` exactly as `ps`
does. A host with Chrome, java or kubelet running would show one mismatch per
such process. The synthetic table is byte-identical before and after, and
`tests/smoke.sh` still passes.

## Also in this area (not patched)

`read_cmdline` collapses runs of NUL, so an empty argv element (`""`) becomes one
space rather than disappearing; `ps` drops empty elements. Same function, same
one-line place if you want it exact.

## Environment

psgen 0.0.1-beta.1 x86_64-unknown-linux-musl, unprivileged, Linux 7.2.11,
procps-ng 4.0.7 as `ps`.

3a, 3b and 3c all reproduce here on `bf80156`; 3d needs a process with a 7+ digit VSZ, which this cage cannot create (no CAP_SYS_RESOURCE for a large mapping), so it stays code-read for me.

3a — the newline case, with `python3 -c` argv containing `\n`, `\t` and `\x01`:

```
$ psgen table --live | grep -A2 line1
966         3191  0.0  0.0  20484  9128 ?        S    02:21   0:00 /usr/bin/python3 -c import time;time.sleep(20) line1
line2 tab	here ctl

   3191 /usr/bin/python3 -c import time;time.sleep(20) line1 line2 tab?here ?ctl
```

```
$ ps -o pid,stat,args -p 426 --no-headers

966          426  0.0  0.0      0     0 ?        Zs   02:14   0:00 [postgres]
```

3c — `inject --table` order: `3254 3252 3249 3253 3250 3251` on a 6-row run (out of order 5 runs out of 5). Your one-line `rows.sort_unstable_by_key(|p| p.pid)` in `live::read_pids` fixes it; sorting at the `--table` call site also works.

Three `tests/invariants.py` additions would catch these: compare `table --live` offsets against `ps aux` for a wide-VSZ row, assert `<defunct>` for a `/proc/PID/stat` state of `Z`, and assert `inject --table` PIDs are ascending. 3c is fixed on the branch `qa/verified-fixes` in `Nemo-010/psgen`; 3a/3b/3d are not touched by it.
