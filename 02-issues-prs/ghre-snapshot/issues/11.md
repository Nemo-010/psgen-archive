## What the pipeline does today

`.github/workflows/ci.yml` and `release.yml` are in good shape: actions pinned by
SHA, `persist-credentials: false`, `cargo build --locked`, a staged binary and
`tests/smoke.sh`, per-target static checks (`readelf -d … NEEDED`,
`readelf -l … INTERP`), qemu binfmt installed only for the cross targets,
reproducible tarballs (`--sort=name --mtime='UTC 1970-01-01' --numeric-owner`,
`gzip -9n`), `SHA256SUMS` computed in `dist`, build provenance attestations, and
`--prerelease` chosen by the `-` in the tag.

Checked by hand on the published release: all seven raw binaries verify against
`SHA256SUMS`, all seven are static (no `INTERP`, no `NEEDED`), four are
static-PIE and three are not (`aarch64`, `armv7`, `i686`, `ppc64le`), and the
`sandbox` install snippet from the README works verbatim.

Four gaps worth closing before the next tag.

## 11a. Nothing checks style or lints

No `cargo fmt --check`, no `cargo clippy -D warnings`, no `cargo deny`/`cargo
audit`, no MSRV job. The dependency surface is `libc` alone, so the supply-chain
risk is small, but the lint pass is free and finds real things in this tree
today — `let _ = mem_total;` in `live::read_pid` (a parameter the function
stopped using), the now-dead `tty_start`/`tty_len` block in `table::render` after
the fix in issue #3, `needless_range_loop` shapes in `str.rs`, and
`&Vec<u8>`-taking helpers that `&[u8]` would cover. It would *not* catch the
off-by-one in issue #1 (there is no lint for a slice/literal length mismatch),
which is why the test in that issue matters more than any lint. Suggested steps
in the `test` job:

```yaml
      - name: fmt
        run: cargo fmt --all -- --check
      - name: clippy
        run: cargo clippy --locked --all-targets -- -D warnings
```

(`--all-targets` includes `tests/` and `bench/` Python? No — only Rust targets;
the Python checks below are separate.)

## 11b. The cross-target binaries are only smoke-tested with `--version`

`release.yml` runs `target/<t>/release/psgen --version` under qemu, which proves
the binary loads and the RNG/formatting does not trap. It does not prove the
musl `getpwnam_r`, `pidfd_open`, `/proc` parsing or the stub's `execve` path work
on another architecture — and the stub is the part with the most
architecture-dependent code (`libc::syscall` numbers, `SYS_open_tree`,
`SYS_move_mount`, `close_range`, `ioctl` request types).

The cage already installs binfmt for `arm`, `riscv64`, `loong64` and `ppc64le`;
`tests/smoke.sh` needs `target/release/psgen` staged, which is a two-line step:

```yaml
      - name: smoke (cross, under binfmt)
        if: matrix.qemu != ''
        run: |
          set -eu
          mkdir -p target/release
          cp "target/${{ matrix.target }}/release/psgen" target/release/psgen
          sh tests/smoke.sh
```

The smoke suite is unprivileged and, with the patches in issue #6, skips the pty
and root-only checks, so this should pass on qemu in a default GitHub runner.

## 11c. `crates.io` carries only a `0.0.0` reservation

```
$ curl -s https://crates.io/api/v1/crates/psgen | head -c 200
{"crate":{"id":"psgen","name":"psgen", … "default_version":"0.0.0",
 "num_versions":1, … "description":"Reserved crate name for the p…"
$ curl -s https://crates.io/api/v1/crates/psinject | …
```

Both names were reserved 2026-11-08 with a `0.0.0` placeholder and a "Reserved
crate name" description. `README.md` documents this ("The crates.io names `psgen`
and `psinject` are reserved; no functional crate is published"). Two costs:

* crates.io's name policy lets a name be reclaimed when the only version is a
  placeholder and it stays unused — the reservation is not permanent;
* `cargo install psgen` (the first thing anyone tries) installs a 0.0.0 stub or
  fails.

Publishing the real crate from the release job closes both:

```yaml
  publish:
    needs: [test, build]
    if: startsWith(github.ref, 'refs/tags/v') && !contains(github.ref_name, '-')
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      id-token: write        # crates.io trusted publishing, no token secret
    steps:
      - uses: actions/checkout@… # pinned
      - run: cargo publish --locked --dry-run    # then drop --dry-run
        env:
          CARGO_REGISTRY_TOKEN: ${{ secrets.CARGO_REGISTRY_TOKEN }}
```

(trusted publishing avoids the long-lived token entirely; `--dry-run` first so a
`cargo package` problem — a missing `readme`/`license-file`, an unignored
`target/` — fails before the upload). `Cargo.toml` also has no `repository`,
`homepage`, `keywords`, `categories` or `rust-version`; `cargo package` warns
about none of those but the crates.io page looks empty without them.

`README.md` also says "no GNU/glibc artifacts are published" — worth keeping, but
then `cargo install` builds a glibc binary from source, which contradicts the
"static musl only" claim in the *artefact* sense; a `#[cfg(target_env = "gnu")]`
note or a `cargo install --target x86_64-unknown-linux-musl` line in the README
would make it explicit.

## 11d. Two smaller ones

* `.github/release-notes.md` is a fixed file, so every release after this one will
  claim "Static Linux binaries for psgen 0.0.1" and mention no changes. Either
  generate it from `CHANGELOG.md` for the tag, or pass
  `--generate-notes` and append the file.
* `unit` (and the README) claim `After=local-fs.target proc-fs-nets.target`;
  systemd ships no `proc-fs-nets.target` (checked against `units/meson.build` on
  `systemd` main: 47 `.target` units, no such name), so every boot logs
  `Failed to add dependency on proc-fs-nets.target, ignoring`. That is in the
  `unit` issue, not here — mentioned so CI's `systemd-analyze verify` idea has a
  first case to catch:

  ```yaml
      - name: unit
        run: |
          sudo apt-get install -y systemd
          ./target/release/psgen unit > /tmp/psgen.service
          systemd-analyze verify /tmp/psgen.service
  ```
