## Body

## What happens

`stop` reports processes stopped that are already dead, because a zombie still
answers `/proc/PID/stat` and `/proc/PID/comm` with the same starttime and comm
the pidfile recorded:

```
$ psgen inject -n 6 -s 7 --pidfile /tmp/p.pid -q
$ psgen stop --pidfile /tmp/p.pid
stopped 6 processes
$ psgen stop --pidfile /tmp/p.pid
stopped 3 processes, skipped 3      # three of them died minutes ago
```

`ps` shows what those three are:

```
$ ps -o pid,stat,args -p 433,434,435
    433 Zs   [flanneld] <defunct>
    434 Zs   [cron] <defunct>
    435 Z    [nginx] <defunct>
```

Signals to a zombie are accepted and discarded, so `kill(-pgid)` and
`pidfd_send_signal` both "succeed", `count` goes up, and the `# temp` cleanup
path (`failed == 0`) runs on the strength of it. A caller writing
`psgen stop --pidfile … && rm -f …` cannot tell a real stop from a no-op.

Cause: `src/inject.rs`, `stop()`. The identity check is correct and necessary,
but it is not a liveness check.

## Patch

```diff
--- a/src/inject.rs
+++ b/src/inject.rs
@@ -1206,6 +1206,13 @@
         if pid == sys::getpid() {
             continue;
         }
+        // A zombie is already dead. Its /proc entry still answers starttime
+        // and comm, so without this a second `stop` reports it as stopped.
+        if live::read_stat(pid).map(|s| s.state == b'Z').unwrap_or(false) {
+            skipped += 1;
+            continue;
+        }
         let pfd = sys::pidfd_open(pid);
```

`live::read_stat` is already public and already parsed by this module, so no new
surface. Verified on five consecutive 6-row runs, each followed by a second `stop` after
half a second: every second run printed `stopped 0 processes, skipped 6` (before
the patch it was `stopped 3 processes, skipped 3`, and on a longer table
`stopped 3 processes, skipped 3` twice in a row). With no gap at all, one PID can
still be counted because the first kill has not landed yet — see the second half
of this issue. The repository suite passes with the patch.

## Related, worth fixing in the same pass: `stop` reports success too early

One more accounting nit in the same function: the *first* `stop` already reports
`skipped N`, because a child killed through its parent's process group is gone by
the time its own pidfile line is processed. So `stopped` is a count of signals
delivered and `skipped` a count of lines that needed none, not "N stubs stopped".
A caller that wants a number uses the pidfile line count; the README says
nothing about which is which.

`stop` counts a process as stopped as soon as `kill(-pgid, SIGKILL)` returns,
which is before the process has exited. Observed once during testing:

```
$ psgen stop --pidfile /tmp/p.pid
stopped 4 processes
$ awk '{print $3}' /proc/4989/stat
R                                   # still running
```

A short bounded wait makes the report true and also makes the `# temp` removal
correct (a temp dir must not be removed while a stub is still writing to it):

```rust
// after the signal loop, before the temp cleanup
for (pid, start, _comm) in &result_ident {          // identities captured above
    for _ in 0..200 {                               // ≤2 s
        if live::read_starttime(*pid) != Some(*start) { break; }
        sys::nanosleep(0, 10_000_000);
    }
}
```

`--wait` already does this (it polls and reaps); `stop` does not. Both the
"zombie" and "still running" cases are the same defect from the caller's point
of view: the exit code and the count do not mean what they say.

## Environment

psgen 0.0.1-beta.1 x86_64-unknown-linux-musl, unprivileged, Linux 7.2.11, in a
container whose PID 1 does not reap (so the killed stubs stay zombies). On a host
with a reaping init the zombie case is rarer but still reachable for the window
between `kill` and `wait`.

### Nemo-010 - 2026-11-09T03:37:16Z

Both halves reproduce here, and the first half is worse than "counts zombies": the count is also timing-dependent because of the *order* the pidfile is walked.

```
$ psgen inject -n 6 -s 7 --pidfile /tmp/z.pid -q
$ psgen stop --pidfile /tmp/z.pid
stopped 6 processes
$ sleep 1; psgen stop --pidfile /tmp/z.pid
stopped 3 processes, skipped 3
$ sleep 1; psgen stop --pidfile /tmp/z.pid
stopped 3 processes, skipped 3
```

The second and third `stop` both report "stopped 3" for the same three zombies, i.e. the count is a count of *signals accepted*, and a zombie accepts them.

The subtree half, on a 40-row run, three times:

```
$ for i in 1 2 3; do psgen inject -n 40 -s 7 --pidfile /tmp/s.pid -q; psgen stop --pidfile /tmp/s.pid; done
stopped 33 processes, skipped 7
stopped 35 processes, skipped 5
stopped 34 processes, skipped 6
```

Root cause for that half: the pidfile is written in ascending PID order, so a root is always signalled before its children, and its process-group kill reaps them before their own lines are reached.

Signalling the deepest PIDs first (reverse the line order) gives `stopped 40 processes` three times out of three, and reading `/proc/PID/stat` once per line for both starttime and pgrp removes the extra read that widened the race. That plus a `Z` check before signalling is staged on `qa/verified-fixes` in `Nemo-010/psgen`; the zombie check is still open there, because it changes the meaning of `stopped` and that is your call.

Your bounded-wait suggestion after the signal loop is the other half of making the count true; I did not add it, since it delays `stop` by up to 2 s on a slow host.
